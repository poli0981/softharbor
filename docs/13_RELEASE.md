# 13 — Release & Operations

## 1. Versioning model

The **site** deploys continuously from `main` — no version numbers on
content. Git tags mark milestones only: **`v1.0.0`** at public launch
(tagged and released 2026-07-30), **`v1.1.0`** for the post-launch review
(tagged and released 2026-10-21; `package.json` `version` follows the tag),
**`v1.2.0`** for the upkeep release — re-check automation, Node 26 /
TypeScript 7, CI-based SonarQube Cloud, catalogue batch 2 (2026-10-23),
**`v1.3.0`** for the site-wide rate limit (D32, 2026-10-26),
minor tags when a feature phase ships. Publishing a GitHub Release fires `notify.yml` →
Discord (docs/12 §2). Data changes never tag. `CHANGELOG.md`
(Keep-a-Changelog, dates UTC) records feature work and anything a visitor
should know — v1.1.0 leads with the privacy changes — not app additions:
the RSS feed *is* the data changelog.

## 3. Release sequence (every merge, every tagged release)

**After every merge to `main` — verify production, never assume it.**
Workers Builds runs one build at a time; after a burst of PR pushes a
`main` merge can wait about 20 minutes, and a superseded queued `main` build
may be skipped (docs/12 §3).

1. **Wait** until the merge commit's **"Workers Builds" check is green**
   (check run `Workers Builds: softharbor`, beside `build`, `gates` and
   `codeql`). The check appears only once the build *starts* — no check
   yet means "queued", not "failed".
2. **Then verify production itself:**
   - the new content-hashed `/_astro/` asset names are served (compare the
     page source with the local `dist/`), so the new build is live;
   - the headers: `curl -sI https://softharbor.net/` — header CSP exactly
     `frame-ancestors 'none'`, the security headers, HSTS; one hashed asset
     with a single `Cache-Control: public, max-age=31536000, immutable`;
   - the per-page CSP meta lists the two Cloudflare origins (docs/09 §4);
   - `/api/verify` is answered by the **Worker**:
     `curl -s -X POST -H 'Origin: https://softharbor.net' -H 'Content-Type:
     application/json' -d '{"token":"x"}' https://softharbor.net/api/verify`
     → `403 {"error":"rejected"}` (a `503 not_configured` means the runtime
     secret is missing; a bare `405` from the asset server means the Worker
     is not deployed);
   - the site-wide rate limit (D32, docs/08 Part F) answers a burst over
     **one connection** — one `curl` with many URLs reuses its connection;
     parallel `curl`s would land on different machines and pass (Part F):
     `curl -s $(for i in $(seq 70); do printf -- '-o /dev/null https://softharbor.net/robots.txt '; done) -w "%{http_code}\n" | sort | uniq -c`
     → about 60 × `200`, then `429`s; add `--next -s -D - -o /dev/null
     https://softharbor.net/apps` to the same command to see a refused
     page: `429`, `Retry-After: 10`, `Cache-Control: no-store` and the
     `_headers` set. Ten seconds later everything is `200` again;
   - `/rss.xml` serves the expected items (guid = slug, docs/05 §A4).
3. **Never run `wrangler deploy` by hand while builds are queued** — the
   queued older build would land after it and roll production back
   (docs/08 A3).

**Tagged release** (`v1.1.0` and later):

1. Merge (squash, signed — docs/12 §8), then complete the three steps above.
2. Update `CHANGELOG.md` and `package.json` `version`; tag `vX.Y.Z` and
   publish the GitHub Release — **release notes must be accurate before
   publishing**: `notify.yml` announces them to Discord at once (docs/12 §2;
   the manual re-run takes a `tag` input, passed on as `tag_override`).
3. Manual posts where the automation doesn't reach (Discord announcement
   channels with role pings, pinned messages).

**Launch day (v1.0.0, 2026-07-30)** followed the same shape: final seed PR
merged → production verified → tag + release → Discord via `notify.yml` →
manual posts → the RSS → notify.py cron enabled for ongoing per-app
announcements (§5).

## 5. Ongoing announcements (notify.py integration)

The existing cross-poster consumes `/rss.xml` (guid = slug, docs/03 §7) on
its GitHub Actions cron and posts new items to Telegram, Discord webhook,
Bluesky, Mastodon, X, Facebook. It announces **every `<guid>` it has not
seen**, so its failure modes are public and irreversible. SoftHarbor-side
contract: never reuse or rename a slug; never backdate `addedAt`; the feed
stays deterministic (pinned collator, docs/05 §A4); never change the guid
shape or the 50-item window's order without meaning to announce.
`check:feed` enforces the emitted shape on every build. Message template
(configured on the notify.py side):
`🆕 {name} — {summary.en} · {site}/apps/{slug}`.

## 6. Operating cadence

| Cadence | Task |
|---|---|
| per-PR | vetting checklist on new/changed entries |
| **after every merge** | wait for the merge commit's "Workers Builds" check, then verify production (§3) |
| daily (auto) | quarantine sweep (docs/12 §4) |
| weekly (auto) | link-check triage — the one `link-rot` issue is refreshed or closed (docs/12 §5); fix, replace with official mirror, or flag |
| weekly (auto, Monday) | Dependabot PRs (npm + actions, 2-day cooldown) — merge when CI is green; osv/audit findings fail CI on their own |
| daily (auto, 00:41 UTC) | VirusTotal re-check (docs/12 §4b): checks older than 90 days are re-scanned into the one `vt/recheck` PR — review and merge it; triage any `[vt] <slug>` issue (false positive → back to `clean` with a note; confirmed → `flagged` + `pnpm quarantine`). GitHub disables a public repo's schedules after 60 days without activity — re-enable the workflow if it ever goes quiet |
| monthly (manual, ~10 min) | GSC review: Coverage, Core Web Vitals, hreflang errors; skim DMARC reports (docs/16 §6/§8) |
| **annually (manual, ~2 min)** | **Roll `Expires` in `public/.well-known/security.txt` forward one year** (docs/09 §5). An expired `security.txt` is treated as invalid by scanners and researchers — and nothing else in this repo would notice. |
| once, post-launch | HSTS phase transitions P1 → P2 (+2 weeks) → optional P3/preload (H9) — docs/16 §5. Observed 2026-10-21: already at P3 (`preload` in the header) — docs/15 §5 |
| quarterly | review category taxonomy & criteria rulings; prune tags |

## 7. Incident playbook (listed app turns out harmful)

1. Set `flagged` and run `pnpm quarantine` in the same PR (`validate:data`
   rejects a flag left in place); the nightly workflow is the safety net
   for anything that slips through. Site updates once the merge has
   deployed — verify it (§3).
2. Tracking issue gets evidence links; entry's page 404s (acceptable — the
   RSS item remains historical, do not rewrite the feed).
3. If users were plausibly exposed (app was `clean` at the time), post a
   notice via the announcement channels referencing the issue.
4. Post-mortem line in the decision log: which checklist step failed, and
   whether §6 cadence or docs/09 §6 needs tightening.
